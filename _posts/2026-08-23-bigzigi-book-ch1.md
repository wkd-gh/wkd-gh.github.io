### <i class="fas fa-book fa-fw"></i> **왜 이 책을 골랐나**

이미 실무에서 하둡, 하이브, 스파크는 이름 정도는 익숙한데, 정작 "이 기술들이 왜 이 순서로 등장했는지"는 제대로 정리해본 적이 없어서 골랐다. 1장은 그 역사를 훑어주는 개론 성격이 강했다.

### <i class="fas fa-server fa-fw"></i> **Hadoop과 NoSQL, 빅데이터 기술의 두 축**

책은 빅데이터 기술의 대표 예로 Hadoop과 NoSQL 두 가지를 꼽는다.

Hadoop은 구글이 개발한 분산 처리 프레임워크 맵리듀스를 참고해서 만들어졌다. 근데 초창기엔 진입장벽이 꽤 높았던 모양이다 — 뭘 하나 집계하려 해도 자바로 프로그래밍을 해야 했다고 한다. 이 벽을 낮춰준 게 2009년에 나온 Hive다. Hive 덕분에 프로그래밍 없이 SQL만으로 데이터 집계가 가능해졌고, 이게 하둡 대중화의 실질적인 시작점이었던 것 같다.

NoSQL은 방향이 좀 다르다. 기존 RDB의 제약(고정된 스키마, 수직적 확장의 한계)을 없애자는 목표로 등장했고, 책에서는 크게 세 종류로 나눈다.

| 종류 | 설명 |
| --- | --- |
| Key-Value Store | 키 하나에 값 하나, 가장 단순한 구조 |
| Document Store | JSON처럼 구조화된 문서 단위로 저장 |
| Wide-Column Store | 컬럼을 유연하게 추가할 수 있는 넓은 테이블 구조 |

RDB보다 읽기·쓰기 속도가 빠르고 분산 처리에 강하다는 게 공통된 장점이다. 그래서 Hive(SQL 집계)와 NoSQL(고속 저장)을 조합해서, NoSQL에 데이터를 저장하고 하둡으로 분산 처리하는 조합이 2011년 말부터 퍼지기 시작해서 2012년부터 본격적으로 유행했다고 한다. "현실적인 비용으로 데이터를 처리할 수 있게 됐다"는 문장이 인상적이었는데, 결국 빅데이터 기술의 확산은 성능보다 **비용 문제를 얼마나 풀었는지**가 관건이었던 것 같다.

### <i class="fas fa-clock-rotate-left fa-fw"></i> **빅데이터 기술 연표로 정리해보니**

책 본문은 시간순으로 딱 정리된 서술이 아니어서, 읽으면서 등장 시점 기준으로 다시 나열해봤다.

```mermaid
flowchart LR
    A["Hadoop 등장\n(MapReduce 참고)"] --> B["Hive\n2009"]
    B --> C["BigQuery\n2010.5"]
    C --> D["Hadoop+NoSQL 조합\n2011~2012 유행"]
    D --> E["Redshift\n2012.11"]
    E --> F["Spark 보급\n2013~"]
```

이렇게 줄 세워 놓고 보니 흐름이 좀 더 명확해졌다. Hive가 하둡의 진입장벽을 낮췄고, 그 직후 BigQuery·Redshift 같은 클라우드 DW가 등장하면서 "굳이 하둡 클러스터를 직접 운영하지 않아도" 대량 데이터를 다룰 수 있는 선택지가 생겼다. Spark는 그 다음 순서로, 기존 맵리듀스보다 효율적인 분산 처리 방식으로 자리를 잡았다.

### <i class="fas fa-scale-balanced fa-fw"></i> **하둡 vs 데이터 웨어하우스, 언제 뭘 쓰나**

일부 기업들은 하둡 대신 데이터 웨어하우스(DW)를 도입했다고 하는데, 이유가 재밌었다. DW는 보통 하드웨어와 소프트웨어가 통합된 장비 형태로 제공돼서 안정적인 성능은 보장되지만, 반대로 데이터 용량을 늘려야 할 때는 확장성이 떨어진다는 단점이 있다고 한다.

| 항목 | Hadoop | 데이터 웨어하우스 |
| --- | --- | --- |
| 적합한 데이터 | 가속도적으로 늘어나는 대용량 데이터 | 비교적 작고 중요한 데이터 |
| 확장성 | 노드를 추가하는 방식으로 유연하게 확장 | 통합 장비 형태라 용량 증설 시 확장성이 낮음 |
| 성능 안정성 | 상대적으로 변동 있음 | 통합 장비 덕분에 안정적 |

![Hadoop과 데이터 웨어하우스의 확장 방식 차이](hadoop_vs_dw_scaling.svg){: width="1000" height="440" }
_Hadoop은 노드를 옆으로 붙여 확장하고, DW는 통합 장비 자체를 교체해야 확장할 수 있다_

그래서 "가속도적으로 늘어나는 데이터는 하둡, 비교적 작고 중요한 데이터는 DW"라는 식으로 역할을 나눠 쓰는 게 당시엔 자연스러운 선택이었던 것 같다. 지금 기준으로 보면 좀 옛날 얘기처럼 느껴지긴 하는데, 왜 클라우드 DW가 그 다음 국면을 열었는지 이해하는 데는 이 배경이 필요했다.

### <i class="fas fa-cloud fa-fw"></i> **클라우드가 DW를 바꿔놓다**

앞서 연표에도 넣었듯, 2010년 5월 구글 BigQuery, 2012년 11월 AWS Redshift가 등장하면서 상황이 바뀐다. DW를 클라우드 서비스로 쓸 수 있게 되면서, 이전처럼 통합 장비를 직접 들여놓지 않고도 작은 프로젝트 단위에서 자체적으로 분석 기반을 마련할 수 있게 됐다.

이 흐름을 타고 2012년부터는 "데이터 디스커버리"라는 게 유행했다는데, DW에 있는 데이터를 대화형으로 시각화하는 프로세스라고 한다. 지금 감각으로는 그냥 셀프서비스 BI 도구 얘기 같다. 그리고 2013년 이후부터는 맵리듀스보다 효율적인 분산 처리 시스템으로 Apache Spark가 보급됐다고 하는데, 이 부분은 실무에서도 이미 많이 접해본 내용이라 새롭진 않았다.

### <i class="fas fa-diagram-project fa-fw"></i> **데이터가 흘러가는 전체 그림**

1장 후반부는 지금까지 나온 기술 조각들을 하나의 파이프라인으로 엮어준다.

```mermaid
flowchart LR
    A["수집\n벌크형 · 스트리밍형"] --> B["분산 스토리지\n객체 스토리지(S3) · NoSQL"]
    B --> C["분산 처리\nMapReduce · Hive · 대화형 쿼리 엔진"]
    C --> D["DW / 데이터마트\nETL · ELT"]
    D --> E["BI\n데이터 디스커버리"]
```

- **수집** : 원래는 벌크형(배치)이 주류였는데, 모바일 애플리케이션이 늘면서 스트리밍형이 많아졌다고 한다. 이때 시계열 데이터베이스가 쓰이지만, 장기적인 데이터 분석에는 여전히 배치 처리 구조가 유리하다는 언급도 있었다.
- **저장** : 수집한 데이터는 분산 스토리지에 쌓인다. 우리가 흔히 아는 S3 같은 객체 스토리지가 대표적이고, NoSQL 데이터베이스를 분산 스토리지로 쓰기도 한다.
- **처리** : 분산 스토리지의 데이터를 다룰 때는 맵리듀스 같은 분산 처리 프레임워크를 쓰거나, SQL로 집계하려면 Hive 같은 쿼리 엔진, 혹은 Hive보다 빠른 "대화형 쿼리 엔진"을 쓴다고 한다.

책에는 "대화형 쿼리 엔진"이 구체적으로 뭘 가리키는지 명시가 안 돼 있어서 읽으면서 좀 헷갈렸다. Presto인지 Trino인지 아니면 Spark SQL을 말하는 건지 궁금했는데, 예전에 [Airflow Presto/Hive Operator 비교 글]({% post_url 2026-08-16-airflow-sensor-branch-hive-presto-operator %})을 정리하면서 겪었던 경험에 비춰보면 Presto·Trino류의 MPP 쿼리 엔진을 뭉뚱그려 말하는 것 같다. Hive는 내부적으로 맵리듀스/테즈 잡을 거치기 때문에 상대적으로 느리고, Presto·Trino는 잡을 거치지 않고 메모리 기반으로 바로 계산해서 "대화형"이라 부를 만큼 응답이 빠르다.

DW 자체를 외부 제품으로 쓰는 경우엔 ETL·ELT가 필요하고, 이 파이프라인 전체를 관리하기 위한 워크플로 관리 기술(Airflow 같은)이 등장한다는 언급으로 이 파트가 마무리된다.

### <i class="fas fa-quote-left fa-fw"></i> **데이터 먼저, 테이블은 나중에**

아래는 1장에서 개인적으로 가장 기억에 남은 문장이다.

> 우선 데이터가 있고, 나중에 테이블을 설계하는 것이 빅데이터다.
{: .prompt-tip }

![데이터 레이크 개념도](data_lake_concept.svg){: width="1000" height="520" }
_형식이 제각각인 데이터를 일단 레이크에 그대로 모아두고, 필요할 때 스키마를 입혀 테이블로 만든다_

빅데이터 시대가 되면서 ETL 프로세스가 복잡해진 이유가 여기 있었다. 모든 데이터가 처음부터 DW 스키마에 딱 맞게 만들어지지 않다 보니, 정형화되지 않은 텍스트 파일이나 바이너리 데이터를 일단 그대로 받아둘 공간이 필요해졌고, 그게 데이터 레이크다. 구체적으로는 형식을 가리지 않고 임의의 데이터를 담을 수 있는 분산 스토리지가 데이터 레이크로 쓰인다.

돌이켜보면 RDB 중심 사고방식은 "테이블을 먼저 설계하고 그 틀에 맞는 데이터만 받는다"는 순서였는데, 빅데이터는 그 순서를 뒤집는다는 게 이 문장의 핵심인 것 같다. 데이터를 있는 그대로 우선 확보해두고, 스키마는 나중에 필요할 때 그때그때 입힌다는 발상 자체가 지금은 당연해 보여도, 처음 접했을 땐 꽤 낯선 개념이었을 것 같다.

### <i class="fas fa-users fa-fw"></i> **데이터 엔지니어와 데이터 분석가**

데이터 분석에 필요한 기술이 워낙 다방면에 걸쳐 있다 보니 보통 팀 단위로 일한다는 얘기도 나온다. 시스템의 구축·운용·자동화를 맡는 게 데이터 엔지니어, 데이터에서 인사이트를 뽑아내는 게 데이터 분석가라는 구분이다.

데이터 분석 자체도 책에서는 두 갈래로 나눈다.

| 구분 | 확증적 데이터 분석 (CDA) | 탐색적 데이터 분석 (EDA) |
| --- | --- | --- |
| 접근 방식 | 가설을 세우고 검증 | 데이터를 보면서 의미를 읽어냄 |
| 주요 도구 | 통계학적 모델링 | 시각화 |
| 이 책에서 다루는 비중 | 거의 없음 | 이 책 전체가 이쪽에 집중 |

이 책이 EDA에 집중한다는 걸 미리 밝혀둔 게 좋았다. 어떤 걸 다루고 어떤 걸 안 다루는지 범위를 처음부터 명확히 해두니, 앞으로 읽을 내용에 대한 기대치를 잡기가 편했다.

### <i class="fas fa-code fa-fw"></i> **스몰데이터 준비: Python, R**

본격적인 빅데이터 이야기에 들어가기 전 준비 단계로, 스몰데이터를 다루는 대표 스크립트 언어인 Python과 R을 간단히 비교하고, R의 데이터프레임 모델을 파이썬으로 옮긴 라이브러리인 Pandas를 짧게 실습하며 소개한다. 이 부분은 이미 익숙한 내용이라 가볍게 훑고 넘어갔다.

### <i class="fas fa-chart-simple fa-fw"></i> **BI도구와 모니터링**

1장의 마지막은 스프레드시트나 BI 도구로 데이터를 시각화하는 이야기로 마무리된다. 솔직히 말하면 이 파트는 좀 당연한 얘기들의 나열처럼 느껴져서 크게 감흥은 없었다("BI로 시각화하려면 시각화하기 좋은 형태로 데이터를 가공해야 한다" 같은 내용들). 아마 뒤에 나오는 장에서 이 부분을 더 구체적으로 다룰 것 같아서, 일단은 그러려니 하고 넘어갔다.

### <i class="fas fa-flag-checkered fa-fw"></i> **정리**

1장은 본격적인 기술 설명이라기보다, 빅데이터 생태계 전체 지형도를 훑어주는 개론 성격이 강했다. Hadoop·NoSQL이 어떤 배경에서 나왔고, 클라우드 DW가 왜 그다음 흐름을 열었는지, 그리고 수집부터 BI까지 데이터가 어떤 경로로 흘러가는지를 한 번에 정리할 수 있었던 장이었다. 개인적으로는 "우선 데이터가 있고, 나중에 테이블을 설계하는 것이 빅데이터다"라는 문장 하나가 이 장 전체를 요약하는 느낌이다.
