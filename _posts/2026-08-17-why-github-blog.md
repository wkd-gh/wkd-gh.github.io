### <i class="fas fa-boxes-stacked fa-fw"></i> **왜 갑자기 블로그?**

사실 나한텐 쓰다가 버려진 블로그들이 몇 개 있다. 뭔가 배우거나 회고할 게 생길 때마다 이곳저곳에 흩어놓기만 하고, 정작 꾸준히 이어가진 못했다. 이번에 아예 하나로 정리하기로 마음먹은 것도 그래서이다. 지금까지 여기저기 흩어진 기록들을 이 GitHub 블로그로 모으고, 앞으로 쌓이는 것들도 전부 여기에 남기려고 한다.

문제는 블로그란 게 꾸준히 하기가 참 어렵다는 거다. 글감을 정리하고 다듬는 데 생각보다 품이 많이 들어서, 어느 순간부터는 그 자체가 부담이 되어버린다. 그런데 요즘은 상황이 좀 다르다. Claude 같은 AI와 함께 초안을 정리하고 다듬으면서 쓰다 보니, 예전만큼 큰 마음을 먹지 않아도 글 하나를 완성할 수 있게 됐다. 이번엔 이를 믿고 꾸준히 이어가 보려고 한다.

### <i class="fas fa-code-branch fa-fw"></i> **굳이 다른 플랫폼 대신 직접 만든 이유**

velog나 medium, 티스토리처럼 이미 잘 만들어진 플랫폼도 많은데, 굳이 GitHub Pages로 블로그를 직접 지은 이유는 결국 **자유도** 때문이다. 위와 같은 플랫폼은 시작은 편하지만, 레이아웃 하나 손보려 해도 플랫폼이 허용하는 범위 안에서만 움직일 수 있다. 반면 GitHub Pages + Jekyll 조합은 페이지 하나하나, 버튼 하나의 hover 색상까지 전부 내 마음대로 건드릴 수 있다.

### <i class="fas fa-layer-group fa-fw"></i> **기술 스택과 배포 흐름**

이 블로그는 [Jekyll](https://jekyllrb.com/) + [jekyll-theme-chirpy](https://github.com/cotes2020/jekyll-theme-chirpy) 테마 위에, GitHub Actions으로 빌드·배포까지 자동화한 구조이다.

- **정적 사이트 생성기** : Jekyll (Ruby)
- **테마** : jekyll-theme-chirpy (gem 기반, 필요한 부분만 로컬에서 오버라이드)
- **호스팅** : GitHub Pages
- **CI/CD** : GitHub Actions

배포 흐름은 이렇다.

1. `main` 브랜치에 푸시
2. GitHub Actions `build` job이 Ruby 환경을 세팅하고 `bundle exec jekyll build`로 사이트를 빌드
3. `html-proofer`로 깨진 링크·마크업 오류가 없는지 검증
4. 빌드 결과물을 아티팩트로 업로드
5. `deploy` job이 GitHub Pages에 실제로 배포

push 한 번이면 빌드 검증부터 배포까지 자동으로 끝난다는 게 가장 만족스러운 부분이다.

### <i class="fas fa-piggy-bank fa-fw"></i> **비용 없는 백엔드, GitHub 인프라로 쥐어짜기**

이 블로그를 만들면서 세운 목표 중 하나는 "별도 서버 비용 없이 최대한 완결된 서비스를 만들어보자"였다. 그래서 GitHub 생태계 안에서 최대한 많은 걸 해결하려고 했다.

- **호스팅** : GitHub Pages (무료 정적 호스팅)
- **댓글** : Giscus — GitHub Discussions를 사실상 댓글 DB처럼 사용한다. 별도 서버나 데이터베이스 없이, 이 저장소의 Discussions 탭이 곧 댓글 저장소가 되는 구조다.
- **방문 통계** : GoatCounter — 쿠키나 IP를 저장하지 않는 가벼운 무료 통계 서비스로, footer의 방문자 수와 게시글별 조회수를 여기서 가져온다.

지금은 이 정도로도 충분하지만, 나중에는 GA4까지 붙여서 방문 데이터를 좀 더 본격적으로 분석해보고 싶다. 어떤 글이 유입이 잘 되는지, 사람들이 어디서 이탈하는지 같은 것들을 데이터로 직접 들여다보는 재미도 있을 것 같다.

### <i class="fas fa-palette fa-fw"></i> **직접 만드니까 재미있는 것들**

end-to-end로 직접 구축하고 나니, 확실히 다른 플랫폼보다 자유도가 훨씬 높고 운영하는 재미도 배가된다. 뻔한 레이아웃과 제약이 없다는 게 이렇게 쏠쏠한 재미일 줄 몰랐다. 예를 들면 이런 것들이다.

- 이전/다음 게시물 버튼에 마우스를 올리면 전체가 진한 파란색으로 칠해지는 기본 스타일이 마음에 안 들어서, 옅은 틴트 배경으로 직접 바꿨다.
- 파비콘을 새 아이콘으로 바꿨더니 브라우저 주소창 자동완성에서는 여전히 옛날 테마 기본 아이콘이 뜨는 걸 발견하고, 파비콘이 사실 파일 하나가 아니라 여러 크기의 세트로 구성된다는 걸 알게 됐다.
- 본문 목차가 왜 하나도 안 뜨나 봤더니, 테마의 목차 기능이 활성화되려면 섹션 제목이 최소 `h3`는 되어야 한다는 조건이 있었다. 지금 이 글의 섹션 제목들도 전부 그 규칙을 따른 것이다.

관리형 플랫폼이었다면 시도조차 못 했을 자잘한 것들인데, 이런 걸 하나씩 손보는 재미가 생각보다 크다.

### <i class="fas fa-robot fa-fw"></i> **AI와 함께 운영하기**

이 블로그는 글 초안부터 위에 적은 자잘한 커스터마이징까지, Claude Code와 함께 만들어가고 있다. 저장소 루트에 `CLAUDE.md` 파일을 하나 만들어서, 이 블로그만의 규칙과 그동안 겪었던 에러들(미래 날짜로 글을 쓰면 사이트에 안 보인다거나, SVG 이미지에 크기를 안 넣으면 렌더링이 깨진다거나)을 정리해뒀다. 이렇게 해두면 다음에 AI와 다시 작업할 때 똑같은 실수를 반복하지 않고, 이 블로그의 관례를 바로 따라갈 수 있다.

귀찮고 손이 많이 가던 과정들을 AI 덕분에 오히려 즐거운 놀이처럼 할 수 있게 됐다는 게, 요즘 이 블로그를 운영하면서 가장 크게 느끼는 부분이다.

### <i class="fas fa-star fa-fw"></i> **참고한 레퍼런스**

블로그를 이렇게 꾸며볼 수 있었던 데에는 [판뚜](https://www.youtube.com/@pan-ddu)님의 영상과 [블로그](https://panddu.github.io/)의 영향이 컸다. 영상도 블로그도 정말 잘 보고 있고, 이번에 개인정보처리방침을 쓸 때도 판뚜님 블로그의 형식을 많이 참고했다.

### <i class="fas fa-flag-checkered fa-fw"></i> **마무리**

내가 온전히 주인인 공간에서, 내 속도대로 기록을 쌓아간다는 것. 그리고 예전 같으면 귀찮아서 미뤄뒀을 그 과정을, 이제는 AI와 함께 놀이처럼 즐길 수 있게 됐다는 것. 이 두 가지가, 지금 굳이 GitHub 블로그를 시작한 진짜 이유다.
